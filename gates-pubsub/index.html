Building with agents

Status is a hypothesis. How I keep my AI agents honest.

I let a task card move only on evidence that was executed, and I send every event to the session that owns the work. What that caught in October, and what it still misses.

Sasha Demin · Provectus · 2026-11-09 · 6 min read
Key takeaway I treat every status my agents report as a hypothesis, and I let a card move only when code has checked that the claimed command really ran. I also send each event to the one session that can act on it, so the board and the work cannot quietly drift apart.

Snapshot 29 October 2026; every number is a read-only count.

One morning in October, I found that a reviewer on my client's side had asked for changes on my pull requests. The task board showed no movement. No model had failed. A small script of mine that forwards the reviewer's Slack thread was still sending it to yesterday's manager session, which nobody was reading, and nothing I had built watched GitHub reviews at all.

For me, that was the bigger risk of running AI agents at scale. Not that they write bad code, but that the board says one thing, the work says another, and nobody notices until a client asks. I run a fleet of agent sessions that build, review and merge code for a parametric reinsurance client, whose contracts pay out when a measured weather event crosses a threshold. If you run more than one agent and report its status to anyone, you will likely meet this too.

A wrong status costs the client time: their reviewer waits on a fix nobody is making. So I treat every status as a hypothesis and every artifact as the fact, with two rules, each backed by code. First, a card reaches review or done only when its comment cites a command the log shows actually ran. Second, each event is pushed to the session that owns the work, not to a manager. For the client, a "done" on the board points at a logged command instead of a sentence, and their review reaches the agent that runs the work.

01 A status is just a word

On 29 October, I had 67 cards in an active code stage. I cannot check 67 claims by hand every day. So I stopped trusting the status field and started checking the move.

I give every code card the same six stages, from "in progress" through testing, review, merging and a production check to "done". When an agent tries to move a card, a hook I wrote, a small program that runs before the command, reads the card first and can refuse. Think of a turnstile that opens only for a receipt. My hook refuses five kinds of move:

  • Skipping a stage. One step forward at a time.
  • Review or done with no executed evidence. The card needs a comment listing commands, and each must match a command that ran and exited cleanly in a log that a separate hook writes as each command runs. The agent's own words do not count.
  • A move hidden inside a loop, where the hook cannot see which card is moving. Before this check existed, nine cards reached review or done that way with no check at all.
  • "Blocked" with no exit, meaning no named event that would unblock it.
  • A user-facing agent change with no live test in Slack.

From 2 to 29 October the evidence check refused 57 of 693 moves, and nobody used the off switch. I let the model propose, and I let plain code that answers the same way every time own the gate. A well-written paragraph no longer moves a card on its own. I list the gaps that remain in section 06.

02 Comments a busy person can scan

I make every card comment follow one short template: a verdict in 12 words or fewer, then labelled lines for evidence, next step, owner and blocker. A second hook of mine rejects anything else. From 5 to 29 October it sent 341 comments back for a rewrite.

One line matters more than the rest: when a reviewer agent files a finding, I have it name the earlier finding it replaces. If those links are right, code can list a card's open problems without anyone re-reading the thread. Nothing checks the links yet.

03 Push the event to the owner

I do not let a waiting agent poll, because left alone it keeps asking GitHub, the board and Slack "anything new?" and spends their working memory on the answer "no". So I run one small script per source, a watcher, that does the asking and pushes each new event to a single session.

That session is my Coordinator, the agent I use to run live work and hand each topic to a builder, another agent session that writes the code. On 28 and 29 October my board watcher sent it 152 card changes and my GitHub watcher sent 28 reviews and comments. An event is marked sent only after delivery succeeds, so a crash causes a repeat, not a gap.

Back to that October morning. My first fix pointed the watchers at the new manager session, the one that keeps the board and talks to people. Its turn filled with notices marked "no action requested", and it did exactly that: it acknowledged them. The manager owns no code, so a notice there produced acknowledgement, not progress.

Now a start-of-day check I added fails if any watcher points at the manager, or if nothing watches GitHub.

Key takeaways
  1. A card reaches review or done only on a command the log shows ran; in October that refused 57 of 693 moves.
  2. Each event goes to the session that owns the work, never to the manager.
  3. The gate proves something ran, not that the right thing ran: 12 of 636 allowed moves rested on a live test.

04 A report is evidence, not a story

I have my sessions report to each other the same way. A report is a sentence for humans, then structured data: a verdict per request, and for every "done" at least one piece of evidence, the command, file or link plus what was observed. A guard I wrote rejects a "done" with no evidence.

I close every report with four fields: merged, pushed, deployed, approved, each yes, no or not applicable. "Shipped" can mean any of the three. A field can still be wrong, but it cannot be left vague.

05 Silence is not consent

I record a worker that misses its own deadline, or ends in an error, as "no report". Everything it was assigned goes back to unchecked, and my Coordinator nudges that same worker rather than starting a second one. A quiet agent may be inside a twenty-minute test run, and two agents writing one branch is a worse bug than a slow one.

06 What still goes wrong

I know my evidence check proves only that something ran. It does not prove the right thing ran. Of the 636 moves it allowed from 2 to 29 October, only 12 rested on a live test of the running system. The rest rested on a pull request's state, an automated test run or a unit test. A stricter rule, running silently beside the real one, flagged 539 of those moves as resting on weaker evidence than the change called for. Some are real gaps and some are not. Until I sort them, it only watches.

I also built the check to let a move through when it cannot read the card at all: jamming honest work is worse than an occasional miss; in the same window that happened six times. And on 29 October, 488 cards sat in backlog. The gates check each move. They do not decide which card matters.

The takeaway

I read one published result as pointing the same way. In the Agentless study (Xia and colleagues, 2024), on a benchmark of 300 real GitHub issues, picking among the same candidate fixes by majority vote solved 77. Filtering them with tests that were actually run solved 96. On that benchmark, filtering on executed tests beat voting. It does not prove my gate works; my own numbers above are that test, and they are mixed.

This is how I run agents: I treat every status as a hypothesis and every artifact as the fact. I put the gate in code, where a fluent paragraph cannot talk past it. I send each event to the one session that can act on it. And when an agent goes quiet, I write down what that is: no report.
