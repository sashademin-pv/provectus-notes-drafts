Building with agents

My IDE has no file tree. It has a tree of agents.

I work in an agentic IDE where the sidebar is a tree of owners. Here is how I see, steer and audit hundreds of agent threads a month, and what still breaks.

Sasha Demin · Provectus · 2026-11-09 · 6 min read

TL;DR: I organise my agents as a tree of owners instead of a tree of files, so I can always see who is doing what and stop the wrong thing early. I steer live work, give every writer its own checkout and archive each day, so the tree I look at is always today's.

All numbers come from read-only bb commands on my machine, read on 2026-10-29. "30 days" means threads created 2026-09-29 to 2026-10-28. The commands are listed at the end.

When I run a fleet of AI agents, the hard part moves from writing code to knowing who is doing what, and stopping the wrong thing before it reaches a client's repository. This piece is for tech leads and delivery heads who have reached that point. My answer was to change what my IDE shows me. I work in bb (getbb.app), a third-party agentic IDE where the left sidebar is a tree of agent threads, not a tree of files.

In 30 days on a parametric reinsurance client, I ran 596 threads in my sidebar, a median of 20 a day over the 27 days with any. I talk to one of them. The board those threads work from has marked 364 cards done since it started on 2026-09-28, and 349 of them carry a quoted command as evidence. These are my numbers from one setup, not a benchmark. The practices should transfer to other tools, though I have only run them in bb: organise by owner, give every writer its own checkout, steer live work, archive daily.

01The sidebar is the org chart

I know a file tree answers "where is the code". I need my sidebar to answer my actual questions instead. Who owns this? Is it running? Is it stuck? What did it finish?

My tree has three levels.

At the top sit the standing peers, each a thread that lives for one working day. The Project Manager owns the task board and is the only thread allowed to message a person. The Coordinator owns the live engineering work. The Teacher turns every correction into a rule or a check. The Researcher reads sources in full before a decision. The Communicator frames every message that leaves the fleet. They are peers, not parent and child, so archiving one does not archive the others.

Under the peers sit Directors, each owning one unit of work: a pull request, a review fix, a release. A Director plans, spawns the feature sessions that do the building, and reports up.

Of the 596 threads, 410 were Directors, 409 of them with a parent, and 81 were standing peers. The other 105 were feature sessions, scheduled monitor runs, probes and one-off lanes.

02Pins, sections, one worktree per writer

I pin the standing threads at the top; today that is the PM, the Coordinator and the Teacher. I use sections to group a Director with everything it spawned. 500 of the 596 threads sat in a section, so a whole topic folds into one row. Directors end their titles with their current status, such as "(review requested)" or "(parked: host load)", so a folded row still shows the last status they reported.

I keep writers apart with worktrees. bb can give a thread its own git worktree: a separate checkout of the repository on its own branch. My rule is that two agents that write never share a checkout. 93 of the 596 threads got their own worktree.

03The day has a shape

I rebuild the tree every morning and prune it every evening, to keep it small.

The PM starts first. It checks free disk, memory and CPU first, and spawns nothing below 10 GB of free disk. Then it starts today's Coordinator, Teacher and other peers as top-level threads and pins them. Each new peer asks yesterday's counterpart three things: what is done, what is not, what carries over. Unfinished Directors move under today's peer, unpushed work is saved to a named git ref, and only then is yesterday archived.

Archived standing threads had lived a median of about a day: 24.1 hours for the PM (27 threads), 25.5 for the Coordinator (18), 24.5 for the Teacher (20). Archived Directors had lived a median of 3.8 hours (391). 574 of the 596 threads are already archived.

Key takeaways
  1. Organise by owner, not by file: pinned peers on top, one Director per unit of work.
  2. Two agents that write never share a checkout, and yesterday is archived every morning.
  3. Steer live work. A correction that arrives after the build is a correction to the wrong thing.

04Steer, don't queue

A daily tree is only useful if I can change its course mid-flight. The most important verb in bb is not spawn. It is tell.

bb thread tell <thread> --mode steer delivers a message to an agent while it is still working, so it reads the message before its next step, not after it finishes. A correction that arrives after a long build is a correction to the wrong thing.

A guard rejects any message between threads that lacks a short structured note: what is reported, what evidence backs it, what is still open. So when a Director tells the Coordinator "merged", the note has to name the pull request and how it was checked, and the receiver checks it again before believing it.

Here is that check catching one real mistake. On 2026-10-28 a peer thread relayed that a teammate's pull request was approved and ready. The Director told to merge it read the reviews on GitHub first. A reviewer's change request from the day before was still standing under the later approval. It refused to merge. The reviewer approved less than two hours later.

05The board, memory and a model per thread

I keep one shared truth, the tasks board. Since it started on 2026-09-28 it has collected 1,141 cards, 364 of them done. A code card moves through testing, review, merging and production testing to done. A check refuses the move to done unless the card quotes a command that the execution ledger recorded as run with exit code 0. 349 of the 364 done cards carry such a quote; the other 15 were all closed on the board's first morning, before that check landed that afternoon. For a client, that is the start of an audit trail: the card says what was run, not only that it is done.

bb memory is the fleet's long-term recall: 394 compact records. A thread searches it before deciding something that may already be decided.

Each thread picks its provider (581 ran on Claude Code, 15 on Codex) and names its model at spawn. A Director gets a reasoning model, a bounded build a mid-size one, checks the smallest. A spawn that names no model is refused, because an unnamed model defaults to the most expensive one.

06What still goes wrong

I have not made my recurring agent schedules hold up. bb automations run a prompt or a script on a schedule. All six recurring agent schedules I set up are paused today; both recurring scripts still run every hour. One hourly agent monitor ran 77 times; its last run failed with "target thread is in an error state".

More cards wait than are done: 488 sit in backlog against 364 done. A thread can file a card in seconds; deciding which cards matter is still my job.

Archive is not cleanup. An archived thread leaves its worktree on disk, so the morning routine has to prove each tree is pushed or merged and then delete it explicitly.

07What to take from it

I organise by owners instead of files, and I suggest the same to anyone who runs more than a handful of agents. I give each long-lived role one pinned thread, each unit of work a Director with a parent, and every writer its own worktree. I steer live work instead of queueing behind it. I archive daily, so the tree I look at is always today's.

My sidebar became the org chart, and the org chart became the thing I manage. I still read code every day, but I open it from a thread that has already said why it matters.

Method · every number re-derived 2026-10-29 with read-only commands on one machine; the 30-day window is thread creation 2026-09-29 to 2026-10-28 UTC.
  • Threads, roles, sections, worktrees, providers, lifetimes: bb thread list --json (archived threads included and filtered by archivedAt), role from the title prefix, window by createdAt.
  • Pins: live threads with pinnedAt set.
  • Board: bb tasks list --project <board> --limit 500 --json, paged to the end; evidence: bb tasks show <card> --json for each done card, searching comments for an executed: block.
  • Memory: bb memory catalog --scope project|global --json.
  • Automations: bb automation list --project <id> --json (enabled flag, run count, last error).
