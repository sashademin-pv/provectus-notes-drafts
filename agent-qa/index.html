I don't call an agent done when its tests are green

How I develop, test and debug an LLM agent whose answers a reinsurance payout can depend on: I diff the tool calls, run everything twice, and ship every fix with the query it fixes.

Sasha Demin · Provectus · 2026-11-09 · 6 min read
Key takeaway I do not call an agent done because its tests pass; I call it done when the requests it makes match what the question asked for, in every run. I get there by diffing requests between versions, running everything twice, and keeping the failing query of each fix in the test set.

I ship LLM agents to clients who act on their answers, and I do not treat a green test suite as the end of the work. My working definition of done is narrower: the image I ship, asked the same question twice, asks the database for the same things both times, and those requests match what the question asked for. One of my agents gave the right answer by the wrong path, and the scorer passed it.

A user asked: "Using CHIRPS, how unusual was March 2024 in Bogotá compared with its 30-year average?" CHIRPS is a satellite rainfall dataset, and the data lake held less than thirty years of it, so the expected reply was a polite refusal. The agent refused in both of two runs, and the scorer marked both a pass. When I read the log of what the agent asked the database for, it told another story. Before refusing, the agent had twice requested ERA5-Land, a weather-model dataset the user never mentioned.

01Where the bugs hide

I design my agent so that the model reads a question and decides what to request: which dataset, which place, which dates. Plain code then fetches the data and does the arithmetic, and a separate check rejects any number in an answer that did not come from a fetched row. So the model never computes a number, but it does choose the request. A fluent answer built on the wrong dataset can still pass a scorer that reads answers.

I build this for a parametric reinsurance client, which pays out when a trigger such as rainfall crosses a threshold; my agent runs on LangGraph inside Amazon Bedrock AgentCore.

02Comparing requests between versions

So for every agent change I compare requests instead of answers. Each turn logs its tool calls with their inputs: tool, dataset, place, start and end dates, and the reason for any refusal. I build the branch as the same container image that would ship, run it on a separate test copy of the cloud runtime, and replay one question set against both the branch and the current version. The pull request shows a per-question diff of those requests.

That diff, not the scorer, is what caught the CHIRPS case for me.

03Running everything twice

I run every question twice, because an agent asked the same question twice can take a different path. I call a question a flip when it passes in one run and fails in the other. Here are the two baselines of my behavioural test set, each run twice on the deployed agent:

Flips show up in chat too. In a scripted 29-turn conversation run twice at the end of August, four behaviours differed between the runs, and the follow-up "and the 5th of Feb?" resolved to 2020 in one run and 2026 in the other.

So I count a difference between versions as a change only if it holds in both runs of both versions; anything else I report as unstable, not as a regression. I also compare values: the same question answered with data twice, but with different numbers, is a finding on its own. And I report the direct path and the chat path separately, so the chat path's own defects stay visible.

Key takeaways
  1. I diff the requests, not the answers. The scorer passed a refusal built on a dataset the user never named.
  2. I run everything twice. A difference counts only if it holds in both runs of both versions.
  3. I ship every fix with the query it fixes, and keep that pair in the test set for good.

04Every fix ships with its failing query

I ship each fix with a pair: the literal query that failed on the old version and works on the new one, each stable across two runs. The pair then joins the test set, so later versions keep running it.

For CHIRPS, I also changed the expected behaviour: instead of refusing, the agent should use the whole record it holds and name the years it used. On the deployed fix, the eight CHIRPS questions made 16 turns across two runs, and none of them requested ERA5-Land. The old version had requested it in both runs of the original question.

Then I ran twelve related questions twice. Ten passed both runs. One flipped, refusing in one run and answering correctly in the other. And one was blocked even though its requests and all five returned numbers were identical in both runs, because the answer compared 2023 with a 10-year average without saying which ten years. That missing disclosure was enough to keep the fix from being called done.

I version the test set like code. I keep each superseded version byte for byte with its content hash, 42 of them since late July, and I compare a score only with runs on the same version.

05Fixing the class of bug

When a reviewer finds a bug, I resist the tempting fix of patching the quoted sentence. I send each finding to a root-cause pass first, which names the class of failure and the check that let it through.

In early September, follow-up questions failed when the conversation had opened in lowercase, as in "how much rain did bogota get in the last 7 days". A helper recognised earlier context only from capitalised place names or four-digit years. On the demo, 8 of 8 follow-ups of that shape failed, against 0 of 19 others. The code fix was a few lines. The wider gap was that my test set had no questions in that style: the early-September version had 0 of 115 questions opening in lowercase. The version dated October 27 has 7 of 197, and I add real failures from clients and demos in the user's own phrasing.

06What still goes wrong

I have to report that the flip count went up, from 3 of 115 to 19 of 193. The October set has more questions that fetch real data, and the agent changed too, so with two different sets I cannot split the cause. With two runs per side, these are rough signals rather than precise rates.

My checks are slow. Building an image, pointing a runtime at it and replaying a question set twice per side takes hours, and changes to the shared tool package have to merge one at a time. From September 1 to October 28, 183 of the 640 commits merged to the integration branch touched agent code.

No automated check replaces a live turn either. I finish every agent change with a real conversation in the client's own chat workspace, run twice, because a dashboard showing the service is up does not tell you what it answers.

07Where to start

I let the model choose what to request, and I let code own the numbers. I log every request with its inputs, diff those requests between versions, run each comparison twice, and grow the test set from real failures. Then I suggest you pick a question your scorer already passes and read its request log next to its answer. Mine gave the right answer, and the log showed it had taken the wrong path to get there.
